# DeepSeek 跑起來驗證補充範本(對應 CC 的 `run`)

> 用途:**這是補救路徑,不是預設路徑**——正常情況下,「跑起來實測並回報結果」這句話應該直接寫進原任務書(`brief-template.md`)的驗收條件或自查清單裡,讓 DeepSeek 在同一輪完工前就做完,不需要事後另開一趟。
>
> 只有原任務書漏寫、或完工後才發現需要補做一次實測時,才用這份單獨補一趟(在同一個 worktree 上,同一個或新開一個 dsh 會話都可以,不像複審那樣需要全新 context)。

---

## 任務

在 `<worktree 絕對路徑>` 裡把 `<這次改動的功能>` 實際跑起來,走一遍主要使用路徑,回報結果。

## 啟動方式

用專案自己既有的啟動腳本/指令(`package.json` scripts、`Makefile`、README 裡寫的指令),不要自己發明新的啟動方式。指定 port:`<CC 查過 port registry 後填一個沒被佔用的>`。

## 要驗證的路徑

<CC 列 2-4 條具體要走的操作路徑,例如:「開啟頁面 X,填表單送出,確認出現 Y」「呼叫 API `/foo`,帶參數 Z,確認回應包含 W」——不要只寫「確認能跑」這種空泛描述>

## 驗收條件

- [ ] 服務/程式真的啟動成功,沒有啟動期錯誤
- [ ] 上面列的每一條路徑都實際走過一遍,逐條回報 pass/fail
- [ ] 有任何一條 fail,附上錯誤訊息或截圖式描述,不要含糊帶過
- [ ] **收工前把自己啟動的服務/程序關掉**,確認佔用的 port 已經釋放——DSH 那邊留下的孤兒程序跟 CC 這邊一樣是真的問題,不會自動消失

## 環境備註

這台機器的 bash 環境套了輸出壓縮工具(rtk),指令輸出有時只顯示摘要,需要完整輸出時直接呼叫 `/usr/bin/git`(如果驗證過程也要看 diff 的話)。

---

## 完工前自查清單

1. 確認每條驗證路徑都是「真的操作過」而不是「讀 code 覺得應該會動」。
2. 確認啟動的服務/程序已經關閉,port 已釋放。
3. 回報格式:逐條列出驗證路徑 + pass/fail + 有問題的具體錯誤內容。

---

⚠️ **這份模板還沒有真實委派案例跑過**,第一次真的用它時,把實際落差(DeepSeek 會不會忘記關服務、回報格式好不好用)補寫回這份檔案。
